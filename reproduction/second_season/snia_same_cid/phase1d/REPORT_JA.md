# Phase 1D報告書：同一CID測定系列と共有依存の監査

## 結論

凍結した公開資料だけで追跡できる測定系列は**部分的**だった。Phase
1Bで確定した同一CID 30群・69行について、結果を見る前に固定した
`CID + IDSURVEY`クロスウォークを適用すると、38行は公開測光ファイルへ
一意に接続できたのではなく、凍結クロスウォークと公開入力選択規則に
適合する測光入力候補を1件に限定できた。31行では適合候補を確定できず、
各行に異なる一意な適合候補があった群は30群中3群だった。最終`m_b_corr`
行へ至る直接的な実行祖先は、38行を含め確立していない。

一方、公開`PPLUS.yml`内で事前指定した共有パイプラインの設定アンカーは
12/12件すべて確認できた。これは設定レベルの証拠であり、その設定が実行
されて公開277行へ至ったことを示すjob log、run manifest、入出力hash連鎖
ではない。より完全な再構成に必要として事前指定した外部参照資産3件は、
凍結した公開リポジトリの追跡対象には含まれていなかった。

正式完了状態は
`AUDIT_COMPLETE_SHARED_DEPENDENCY_AND_LINEAGE_CLASSIFIED`、公開リリース
充足度は`PUBLIC_RELEASE_PARTIAL_MEASUREMENT_LINEAGE`である。

これは公開再現可能性と来歴の分類であり、共分散の修正、新しいH0推定、
ハッブルテンションの説明ではない。

## 背景と問い

Phase 1Bでは、H0DNの277距離行がPantheon+SH0ES公式表へ1対1で対応し、
その中に同一CID 30群・69行があることを確定した。Phase 1Cでは、
同一CIDのコントラスト空間で見つかった低分散フラグが、公式STATONLY
共分散でも残ることを確認した。

そこでPhase 1Dでは、次の範囲だけを調べた。

1. 69行の各行について、凍結クロスウォークに適合する公開測光入力候補を
   1件へ限定できるか。
2. 同一CID群内の各行の適合候補が異なるファイルblobを指すか。また、
   両行に候補があるファイル対にバイト同一の`OBS:`行があるか。
3. 共通の測光統合、光度曲線フィット、重複CID共分散処理が、凍結した
   公開設定にどこまで記録されているか。
4. より完全な再構成に必要な参照入力が公開リポジトリで追跡されているか。

光度曲線の再フィット、バイアス補正の再計算、サーベイ順位付け、共分散
変更、修正H0の計算は行っていない。

## 結果閲覧前の内部凍結

主監査契約、判定設定、ソースロック、Phase 1B行対応表、事前閲覧記録を、
69行の完全走査前にプロジェクト内部でhash固定した。外部登録機関への
事前登録ではない。ただし設計時に例示ファイルと参照資産1件の
不在を見ているため、完全な結果盲検ではなく「部分的結果盲検」と明記した。

H0DNとPantheon+SH0ES DataReleaseはURL・commitで固定し、主要ファイルを
Git blob、バイト数、SHA-256でも固定した。Pantheon+測光サブツリー自体も
tree object `3facbb99276c7589349d8eceaac218ccd2ad0726`で固定した。

候補ファイルは、追跡済み`.LIST`に1回だけ現れ、`.IGNORE`に含まれず、
Git blobとして存在するものに限定した。その後、`SNID`、`SURVEY`、
任意の`NOBS`を厳格に解析した。候補選択には距離残差、フィット値、
共分散要素、Phase 1Cの結果を一切使っていない。

## 事後CID単独診断

31行の旧status `NO_ACTIVE_PUBLIC_PHOTOMETRY_FILE`を「公開測光データが
ない」と誤読しないため、主結果を見た後に別契約を内部凍結し、昇格禁止の
事後診断を
行った。847件の解析済み有効ファイルを、IDSURVEYを無視して完全一致CID
だけで検索した。

31行すべてに複数の同一CID候補があった。

| IDSURVEY | 行数 | 行–候補レコード数 |
| ---: | ---: | ---: |
| 51 | 7 | 16 |
| 57 | 16 | 39 |
| 65 | 8 | 18 |
| **合計** | **31** | **73** |

候補台帳には系統的な反復パターンがある。コード51の全行には`LOSS`候補、
コード57の全行には`KAIT_DS15`候補、コード65の全行にはCFA4p1ヘッダー
候補が含まれる。ただし、同じCIDの別サーベイ候補も存在するため、CIDだけ
では最終行を割り当てられない。数値コードと生データ系列を橋渡しし得る
`SURVEY.DEF`も、凍結公開リリースでは追跡されていなかった。

このパターンは、結果閲覧前に別契約として内部固定する後続クロスウォーク
監査で検証すべき具体的仮説であり、Phase 1D内の修正マッピングではない。
事後診断の前後で主結果5ファイルの
SHA-256を照合し、すべてバイト不変であることを確認した。

## 科学的解釈

今回、公開資料から38行を特定の凍結クロスウォーク適合入力候補1件へ限定
でき、共有依存を示す設定レベルのアンカーも確認できた。しかし、最終距離
行へ至る実行run、FITRES、品質カット、bias correction、入出力hashの連結
は確立していない。公開設定が参照する3資産も凍結公開リリースでは追跡
されないが、元解析での不存在を意味しない。

同時に、未解決原因はかなり狭まった。一般的なファイル解析失敗でも、
同一CID測光の不存在でもなく、3つの数値サーベイコードと生データ
ヘッダー語彙の間にある、明示的で一意な橋の不足へ集中している。

これだけではPhase 1Cの低分散を説明できない。共有処理と重複共分散は
依存関係であって、原因と実証されたわけではない。また、ファイルblobが
異なり、文字列として同じ観測行がなくても、露光、較正、尤度が統計的に
独立とは限らない。

## 次に進むべき枝

次は、IDSURVEY 51・57・65のクロスウォーク解決を独立フェーズとして、
結果閲覧前にプロジェクト内部で契約とhashを固定するのが最も強い。公式
SNANAサーベイ登録、生成時メタデータ、
または作成者提供の`SURVEY.DEF`など、結果表と独立した根拠から候補
マッピングを宣言し、全行が一意に解決するか検証する。その橋が確定する
前にサーベイ別コントラストや影響度を計算すると、誤った系列帰属を
科学的効果と取り違える危険がある。
